# Инструкции Codex

## Порядок работы

- Для имён файлов используй кебаб-кейс.
- Перед изменениями изучай фактическое состояние проекта и связанные файлы: не предполагай наличие описанного пользователем кода, данных или поведения.
- Обязательно остановись до изменений, сообщи обнаруженный факт и задай пользователю уточняющий вопрос, если запрос:
  - ссылается на код, данные или поведение как на существующие, но их в проекте никогда не было;
  - просит реализовать поведение, которое уже существует.
- Явная просьба создать новую функциональность не является расхождением сама по себе. Не создавай дубликат и не изобретай отсутствующий контекст молча.
- Если задача уже частично или полностью реализована и пользователь подтвердил необходимость изменений, не дублируй решение: отрефактори, объедини и упрости существующий код.
- Выбирай наименее сложное корректное решение, предварительно рассматривая несколько подходов. Сохраняй читаемость, чистую архитектуру и небольшие сущности с одной понятной ответственностью.
- При появлении важных долговременных архитектурных решений обновляй этот файл для будущих сессий.

## Контекст и сборка

- Проект — простой браузерный бот для пошаговой помощи со сбором ресурсов и крафтом в игре; развивай его постепенно, без преждевременного усложнения.
- Стек: TypeScript 5.x, RxJS, SWC и Rollup.
- Слои чистой архитектуры: `domain`, `application`, `infrastructure`, `presentation`.
- Сборка должна создавать один browser-loadable файл `dist/index.js`.
- Деплойный bundle должен быть максимально минифицированным; читаемый bundle не публиковать на GitHub Pages.
- Матрицы эталонов мини-игры упаковывать в bundle без потерь одной Base64-строкой и при запуске один раз декодировать в общий `Uint8Array`; значения яркости не квантизировать, фрагменты представлять без копирования через `subarray`.
- `dist/index.js` деплоится на GitHub Pages через GitHub Actions.
- Автономные Node-инструменты анализа мини-игры держать в `scripts` и не импортировать в browser bundle.

## Архитектура и код

- Спагетти-код неприемлем: доменную логику, сценарии приложения, инфраструктуру и UI не смешивать.
- В проекте действует Observable-only подход к асинхронности: не использовать `async`/`await`, `Promise`-цепочки и Promise-ориентированные прикладные порты. HTTP-запросы, события, таймеры, отмену и композицию операций реализовывать через `Observable` и операторы RxJS; Promise-API браузера сразу оборачивать через RxJS на инфраструктурной или presentation-границе.
- Для каждой операции с `Observable` обязателен контроль жизненного цикла и аудит утечек памяти. Одноразовые потоки явно ограничивать (`take(1)`), длительные подписки хранить у владеющего контроллера и гарантированно завершать через `unsubscribe`/`takeUntil`/сигнал уничтожения; не оставлять подписки, таймеры и обработчики без teardown.
- Добыча, охота и крафт — независимые сценарии; охота работает автоматическим циклом последовательных боёв. Взаимоисключающие единицы работы любых сценариев ставить в общий прикладной `TaskScheduler`; текущая реализация обслуживает готовые задачи честно в порядке FIFO и не содержит знаний о конкретных сценариях. Границы атомарной задачи определяет сам сценарий: для добычи это полный проход от первичного скана до терминального результата сбора, для охоты — получение локации, скан и запрос нападения, для крафта — только чтение рюкзака и отправка пакета готовых запросов. Ожидание `fightFinished()` и откаты крафта идут параллельно другим сценариям и очередь не удерживают. Сценарии сообщают UI о ходе работы через события use case и не управляют DOM напрямую.
- Рецепты профессий держать отдельной доменной моделью, связанной с каноническим `BotResource` через `resourceId`; цвет и уровень рецепта в UI/логах брать из связанного ресурса.
- Экземпляры из `<farm><item>` не являются отдельными ресурсами: это найденные узлы канонического `BotResource`, связанные через серверный `artikul_id`.
- При переносе curl-запроса в код сохранять только URL и HTTP-метод; cookies, session-токены и скопированные браузерные заголовки в репозиторий не добавлять.

## Канонические данные

- Локальную базу игровых локаций и выбранную локацию не хранить. Текущий `area_id` получать перед запуском добычи из `state.area_id` ответа `POST https://w1.dwar.ru/entry_point.php?object=common&action=dummy&json_mode_on=1` через прикладной Observable-порт `getAreaId`.
- Текущая локальная база ресурсов с постоянными id: агат, аквамарин и бирюза.
- В каноническом ресурсе хранить постоянный `articleId` узла добычи: агат — `362`, аквамарин — `363`, бирюза — `364`. Динамический `artifactId` предмета для крафта в локальной базе не хранить: извлекать его из `data-id` элемента рюкзака `li[div_id="AA_<articleId>"]`.
- Длительность добычи хранить в каноническом ресурсе; агат, аквамарин и бирюза добываются по `20` секунд.
- Текущие рецепты: `Пыль агата` (`recipe_id=51536385`, ресурс `agate`, максимум `10`), `Пыль аквамарина` (`recipe_id=51536386`, ресурс `aquamarine`, максимум `10`), `Пыль бирюзы` (`recipe_id=51536387`, ресурс `turquoise`, максимум `10`).
- Ник текущего персонажа фиксирован: `Чамодан`. Заноза — эффект с `artikul_id=2299`; проверять её отдельной внутренней RxJS-функцией через `effect_info.php`, не через список обычных эффектов CanvasUser и не публиковать функцию в глобальном API.
- Локально хранить предмет экипировки `Кирка древнего клана` с постоянным `artifactId=4603356734`; этой киркой ведётся добыча ресурсов.

## UI и состояние

- При загрузке показывать круглую кнопку с киркой. Она перетаскивается и сохраняет позицию в локальном браузерном хранилище.
- По клику на кирку открывать небольшую тёмную игровую панель. При первом открытии располагать её рядом с киркой; затем независимо сохранять позицию панели. Панель закрывается крестиком, перетаскивается, изменяет размер и сохраняет позицию и размер между перезапусками. При восстановлении сохранённый размер сначала ограничивать только размерами viewport, не используя временную позицию ещё не размещённой панели.
- Добычу, охоту и крафт держать на отдельных табах. У каждого таба свои управление процессом, лог и очистка лога без записи об очистке; события направлять только в соответствующий таб. Progress bar нужен только для длительных действий.
- На табе добычи держать кнопку запуска и мультиселект ресурсов; селект локации не показывать.
- Выбор ресурсов и рецептов сохранять в локальном браузерном хранилище.
- Для длительных действий показывать внизу соответствующего таба progress bar высотой около `10px` с названием процесса, длительностью и прогрессом. Таймеры синхронизировать с событиями use case.

## Логи

- В каждом логе хранить максимум `500` сообщений; при превышении удалять самые старые сообщения с начала лога.
- Общий формат строки: `время: сообщение`.
- Ресурсы и мобы выводить как `Название[<level>]`, без `ур.` и пробела перед уровнем.
- Цветные имена и другие выделения рисовать жирным цветным текстом без рамки и фона.
- Успешным событиям задавать общий светло-зелёный тон строки, неуспешным — светло-красный; время оставлять нейтральным, выделения — с собственным цветом.
- На успешный старт сбора писать ровно одну строку `Начата добыча <resource> (num: <serverNumber>)`, где ресурс является цветным выделением.
- Не показывать проценты спокойности/безопасности, технические логи контрольных сканов и диагностику чтения рюкзака.

## Мониторинг биржи

- Мониторинг заявок биржи держать на отдельной вкладке `Мониторинг биржи`. Конфигурации правил и общий целочисленный интервал в минутах сохранять в локальном браузерном хранилище; активный запуск правила не восстанавливать после перезагрузки.
- Каждое правило независимо запускается и останавливается вручную, удаляется крестиком и содержит частичное название `_filter[title]`, качество и минимальную цену за единицу в меди. Пустое название означает любой предмет; совпадением считать заявку с ценой не ниже заданного порога.
- В селекте качества поддерживать `-1` — все, `0` — серый, `1` — зелёный, `2` — синий, `3` — фиолетовый, `4` — красный, `5` — бирюзовый. `_filter[ihave]` всегда передавать как `0`, результаты запрашивать с `_filter[sort]=cost` и `_filter[sort_order]=desc`.
- Список заявок получать POST-запросом `https://w1.dwar.ru/area_auction.php?&mode=request` с form-urlencoded фильтром. Cookies, токены и скопированные браузерные заголовки не хранить: запрос выполняется в текущей same-origin сессии.
- Из HTML ответа читать заявки `#item_list` по ближайшей строке-предку каждого `.bid-container`, не принимая вложенный `<tr>` таблицы иконки предмета за отдельную заявку. Название брать из непустой текстовой ссылки `showArtifactInfo`, постоянный id из `art_id`, количество из `cnt`, цену из `.bid-container` и классов `.mgold`, `.msilver`, `.mbronze`. Отсутствующий номинал монеты означает ноль. Переводить цену в медь по соотношению `1` золото = `100` серебра = `10000` меди.
- Каждый конечный HTTP-запрос проверки ставить в общий `TaskScheduler`. Интервальное ожидание начинается после ответа, идёт параллельно другим сценариям и общую очередь не удерживает; остановка или удаление правила отменяет его текущий запрос, очередь либо ожидание.
- При совпадениях подсвечивать карточку правила бесшовным золотистым мерцанием и показывать найденные названия, количества и цены. Клик по карточке снимает её мерцание до результата следующего запроса этого правила. Список правил прокручивается целиком и не сжимает карточки; видимый список совпадений внутри карточки имеет минимальную высоту `100px`. Кнопка вкладки `Мониторинг биржи` мерцает тогда и только тогда, когда активна другая вкладка и хотя бы у одного правила есть неотреагированное совпадение; при переходе на другую вкладку индикатор возвращается, пока такая карточка не подтверждена кликом или не обновлена следующим ответом без совпадений.

## Приватные сообщения

- Список игроков текущей локации получать POST-запросом `https://w1.dwar.ru/cht_data.php` с `user_type=area`; из `parent.chatUserHtml` читать `data-nick`, `data-level` и `data-clanid`.
- Игроков кланов `32` и `2156` всегда исключать из адресатов приватных сообщений с просьбой снять занозу.
- На табе добычи держать кнопку `Помощь` вместо кнопки списка игроков; активировать её только после события подтверждённой занозы. Рядом держать включённую по умолчанию галочку автоматической просьбы: если она включена, после подтверждения занозы сразу запускать тот же цикл помощи; включение галочки при уже подтверждённой занозе также запускает цикл.
- По нажатию `Помощь` просить снять занозу максимум у трёх новых игроков не ниже `3`-го уровня; в рамках одной in-memory сессии занозы не писать одному нику повторно, а варианты текста выбирать в случайном порядке без повторов, пока не использованы все варианты. Если выбран один адресат, переводить выбранную реплику в простое обращение на «ты», но не дублировать его ник в тексте после адресного тега `prv[<ник>]`.
- Во время активного цикла помощи кнопка `Помощь` превращается в `Отмена` и прерывает текущие запросы или ожидание; после подтверждённого снятия занозы кнопку деактивировать.
- После успешной отправки ждать `60` секунд и повторно проверять занозу через `effect_info.php`: если она снята, завершать сессию с логом; если осталась, повторять раунд с другими игроками.
- Если новых подходящих игроков в текущей локации нет, ждать `60` секунд и повторять поиск, пока не появится хотя бы один новый игрок или не будет снята заноза.
- После снятия занозы очищать список игроков, которым уже отправлялась просьба в рамках этой сессии занозы.
- После запуска цикла помощи параллельно наблюдать только за новыми HTML-сообщениями вкладки чата `Основной`. Первое системное сообщение приватного канала с текстом `избавляет воина Чамодан от занозы` считать подтверждением помощи, ник лекаря извлекать из аргумента `userPrvTag(...)`, затем через случайные `5–10` секунд отправлять ему одну случайную благодарность: `спасибо!`, `:drink:` или `:mol:`. Ожидание и отправка благодарности не должны менять состояние или результат основного цикла помощи.
- После подтверждённого снятия занозы сначала экипировать `Кирку древнего клана` GET-запросом `action_run.php?code=PUT_ON`, затем автоматически продолжать добычу с актуальным выбором ресурсов; успешным считать HTTP-ответ без ошибки.
- Приватное сообщение отправлять POST-запросом на `https://w1.dwar.ru/entry_point.php?object=chat&action=send&json_mode_on=1` с form-urlencoded телом; скопированные cookies, session-токены и браузерные заголовки не хранить.
- `msg_text` формировать как последовательность адресатов `prv[<ник>]`, разделённых пробелами, затем пробел и текст сообщения: `prv[Дядюшка-А-У] спасибо!`; для нескольких адресатов — `prv[ZEN80] prv[Tyhon] prv[tuborg22] спасибо!`.
- Перед каждой отправкой получать `loc_id` как текущий `area_id` через существующий прикладной Observable-порт `getAreaId`; локально локацию не хранить.
- `crc` не генерировать локально: официальный игровой `js/cht.js` берёт его из выданного сервером `CHAT.session_crc`. Перед отправкой читать актуальное значение из живого chat-frame; cookie `sess_crc` является другим значением.
- В тело также передавать `json_mode_on=1`, `object=chat`, `action=send`, `channel_talk=1`, `private=0`, пустые `complain` и `complain_nick`, `stime=0`, `report[id]=0`, `report[action]=0`, `report[crc]=0`.
- Успешную отправку приватного сообщения подтверждает `status=100` вложенного объекта ответа `"chat|send"`, а не корневого JSON.

## Аварии и мини-игра

- При неожиданном ответе на запрос старта сбора сначала проверить занозу. Если она есть, завершить добычу с соответствующим логом и однократным звуковым сигналом; если занозы нет или проверка не удалась, обработать ответ как аварию.
- Неожиданные ответы сервера на HTTP/XML/JSON-запрос считать аварией: остановить соответствующий процесс и записать красное `ТРЕБУЕТСЯ УЧАСТИЕ ЧЕЛОВЕКА`. Сирену, тревожный оверлей и повторяющиеся звуки не использовать.
- При обнаружении мини-игры звуковой сигнал не проигрывать. Один раз проигрывать короткий мультяшный сигнал только при обнаружении занозы. В шапке держать общий регулятор громкости: клик по иконке переключает mute, вертикальный слайдер меняет громкость; уровень, включая mute, сохранять в локальном браузерном хранилище.
- Ответ охоты с атрибутом `time_left` считать запросом мини-игры: выполнить `GET hunt_conf.php?mode=farm&action=minigame_get` как `Blob`, распознать изображение в памяти и вывести в лог исходное изображение и цепочку без кнопки решения. Перед автоматическим `POST action=minigame_check` с серверной последовательностью и сгенерированной телеметрией `m` выдерживать случайную паузу от `5` до `10` секунд. Исходный PNG без декодирования или перекодирования скачивать только после неудачного результата `minigame_check`; при успешном результате не скачивать.
- После получения ответа `minigame_check` запомнить его статус и отправить `GET action=cancel` без ожидания и обработки ответа отмены. Сразу после отправки отмены обработать сохранённый статус `minigame_check`: при `status="1"` продолжать текущий режим добычи с новой итерации, не переводя управление в остановленное состояние; при любом другом `status`, включая отсутствующий, прекращать добычу.
- Телеметрию `m` для решения мини-игры формировать независимо от игрового `canvas.utils.ABController`: Base64 от JSON со случайной плавной траекторией из `200..300` переходов мыши и рассчитанной по ним статистикой `info.length`.
- Распознанная цепочка мини-игры всегда является серверной перестановкой индексов `0..5` без повторов: для каждой целевой позиции она содержит индекс исходного фрагмента (`targetToSourceSequence`); фрагменты сопоставлять глобально, а не независимыми локальными максимумами.

## Добыча

- Координаты мобов и ресурсов хранить в модели/сторе последнего скана, но не показывать без отдельной задачи.
- Опасный моб имеет `agrlevel > 0` и не является дружественным; `kind="1"` означает дружественного моба. Ресурс безопасен, если в радиусе `100px` нет опасного моба.
- Перед каждой новой итерацией перечитывать текущий выбор ресурсов, а не кэшировать его на весь запуск.
- Цикл: сканировать текущую зону по полученному `area_id`, выбрать самый безопасный доступный узел выбранного ресурса, отправить старт добычи, затем каждые `4` секунды одним контрольным сканом проверять опасность и состояние текущего узла по серверному `num`.
- Кандидатом на старт может быть только узел с `farming="0"`. Любое целое `farming != 0` означает занятый узел: хранить его в скане, но исключать из кандидатов.
- Узлы ресурсов геолога сопоставлять с каноническими ресурсами только по паре атрибутов: `prof="2"` и известный `artikul_id`; совпадения `artikul_id` у других профессий игнорировать.
- После успешного старта текущий узел с `farming="1"` означает продолжающуюся добычу; `farming="0"` — провал, исчезновение узла из `<farm>` — успех.
- Следующую добычу начинать только после успеха или провала текущей, но при терминальном результате раньше `20` секунд переходить дальше сразу.
- Progress bar начинается только после подтверждённого старта и имеет номинальную длительность ресурса (`20` секунд для текущих ресурсов). HTTP-сканы не растягивают таймлайн: после заполнения bar остаётся полным до терминального результата.
- Первичный скан не запускает и не меняет progress bar. Контрольный скан временно меняет только его лейбл, не сбрасывая таймлайн.
- Если безопасного ресурса нет, ждать `20` секунд и повторять цикл. Отмена выполняется запросом `https://w1.dwar.ru/hunt_conf.php?mode=farm&action=cancel`.
- Для каждого запроса старта генерировать новый 32-символьный hex `sig`.
- После старта читать XML `<req>`; если `first_farmer != 1`, сразу отменять добычу и не считать старт успешным.
- Stop во время активного сбора сразу визуально возвращает кнопку в состояние старта, но контрольные сканы продолжаются до терминального результата: успеха, провала, отмены или прерывания. Заполненный progress bar сам по себе отложенный stop не завершает.
- У активной кнопки Stop держать выпадающую команду принудительной остановки: она немедленно сбрасывает локальный цикл и progress bar, отправляет запрос отмены добычи и логирует результат; новый старт блокировать до ответа на отмену.
- Stop во время поиска или паузы срабатывает сразу. Повторный start до терминального результата отменяет отложенный stop и продолжает текущий цикл.

## Крафт

- Крафт выполняется одним общим циклом параллельно добыче.
- Инпут количества не показывать; для каждого запроса брать максимально допустимое для конкретного рецепта количество из локальной базы.
- В начале общей итерации одним GET получать снимок рюкзака для всех выбранных рецептов, затем запускать каждый доступный рецепт. Не запрашивать рюкзак отдельно для каждого рецепта.
- Количество предмета читать универсально по `group` и постоянному `articleId` из HTML `user_iframe.php`: ячейка — `li[div_id="AA_<articleId>"]`, динамический `artifactId` — её атрибут `data-id`, количество — `.artifact-slot-qnt`; если ячейка есть, но элемента количества нет, остаток равен одной единице, а отсутствие самой ячейки означает нулевой остаток. Для текущих камней использовать `group=3`.
- Для каждого доступного рецепта отправлять POST на `service_craft.php`; `amount` равен минимуму из максимума конкретного рецепта и текущего остатка ресурса.
- Если ресурс закончился, остановить только задачу этого рецепта и не перезапускать её в текущем запуске, пока рецепт не будет снят с выбора и выбран снова.
- Общий цикл крафта автоматически завершать только после остановки всех выбранных рецептов из-за исчерпания их ресурсов.
- После успешного запроса логировать количество рецептов и расчётный остаток ресурса; при нулевом остатке логировать остановку рецепта.
- Откаты рецептов одной итерации могут идти параллельно. Progress bar каждого рецепта длится `30 секунд * amount + 5 секунд`; следующую общую итерацию начинать после завершения всех откатов текущей.
- Stop во время активного крафта сразу визуально возвращает кнопку в состояние старта, но завершает цикл только после текущих progress bar; во время паузы stop срабатывает мгновенно.
- Повторный start до завершения старых cooldown ставит продолжение в очередь; новый цикл запускается только после их завершения.

## Охота

- В локальной базе целей охоты хранить `Шальной пёс[1]` с постоянным `artikul_id=19`, `Крэтс[1]` с постоянным `artikul_id=268` и `Крэтс-землерой[2]` с постоянным `artikul_id=2717`; найденный в скане динамический `id` использовать для нападения. Цели в селекте выводить как `Название[level]`.
- Целей охоты и ресурсы получать одним существующим сканом `hunt_conf.php?mode=hunt_farm` по актуальному `area_id`; результат сохранять в общем сторе последнего скана.
- На отдельном табе `Охота` держать селект одной целевой разновидности, кнопку автоматической охоты с состояниями `Начать`/`Завершить`, кнопку `Перезапустить`, лог и чекбокс `Выбирать кучного моба`. Чекбокс по умолчанию выключен. Полный перезапуск немедленно отменяет текущие скан, ожидание или наблюдение `fightFinished()` и запускает цикл заново с текущими настройками. Если бой уже начат, перезапуск заново устанавливает наблюдение за ним и не посылает следующее нападение до `fightFinished()`; `id` предыдущего моба при этом сохраняется.
- Кандидатом для нападения может быть только моб с `fight_id="0"`; мобов с любым другим `fight_id` не атаковать.
- Динамический `id` моба из предыдущего нападения исключать из кандидатов и расчёта кучности следующего нападения: убитый моб может временно оставаться в XML охоты.
- Кандидат безопасен, если в радиусе `100px` нет ни одного недружественного моба с другим `artikul_id`; значение `agrlevel` такого блокирующего моба роли не играет, а `kind="1"` всегда исключается из блокировщиков. Атрибут `hidden` не исключает моба: штатный Canvas использует его только при построении пользовательского фильтра разновидностей.
- Кучность считать по расстоянию до ближайшего другого моба с тем же `artikul_id`: с галочкой выбирать минимальное расстояние, без галочки — максимальное; при равенстве выбирать детерминированно по динамическому `id`.
- Нападение выполнять одним GET-запросом `entry_point.php` с `object=common`, `action=action`, `code=ATTACK_BOT`, динамическим `bot_id`, `url_error=hunt.php`, `in[need_confirm]=1`, `in[confirmed]=0`, `in[tSearch]=0` и cache-buster `_`. В строке лога отправки нападения показывать динамический `id` выбранного моба. Canvas, hunt-frame, AB-телеметрию и открытие игрового UI не использовать.
- Ответ нападения считать успешным только при JSON-поле `redirect_error=false` внутри объекта `common|action` или в корне ответа. Если в ответе есть ключ `farm|minigame`, останавливать цикл и писать красным в лог вкладки `Охота` `Обнаружена мини-игра охоты.` и не запускать обработчик мини-игры добычи. При любом другом теле останавливать автоматическую охоту и выводить исходный ответ как `UnexpectedServerResponseError`; успешный ответ отдельно не логировать.
- После успешной отправки нападения из вкладки `Охота` наблюдать за игровым вызовом `fightFinished()`: он обозначает завершение боя в момент получения боевого результата, а не ручное закрытие окна. После вызова оригинальной функции записывать завершение только в лог охоты, снимать наблюдение и немедленно начинать следующую итерацию поиска и нападения.
- Если подходящего моба нет, не завершать автоматическую охоту: повторять поиск через `5` секунд. Нажатие `Завершить` во время поиска или ожидания останавливает процесс сразу, а во время боя — после текущего `fightFinished()` без запуска следующего нападения.
