# Инструкции Codex

## Порядок работы

- Для имён файлов используй кебаб-кейс.
- Перед изменениями изучай фактическое состояние проекта и связанные файлы: не предполагай наличие описанного пользователем кода, данных или поведения.
- Обязательно остановись до изменений, сообщи обнаруженный факт и задай пользователю уточняющий вопрос, если запрос:
  - ссылается на код, данные или поведение как на существующие, но их в проекте никогда не было;
  - просит реализовать поведение, которое уже существует.
- Явная просьба создать новую функциональность не является расхождением сама по себе. Не создавай дубликат и не изобретай отсутствующий контекст молча.
- Если задача уже частично или полностью реализована и пользователь подтвердил необходимость изменений, не дублируй решение: отрефактори, объедини и упрости существующий код.
- Выбирай наименее сложное корректное решение, предварительно рассматривая несколько подходов. Сохраняй читаемость, чистую архитектуру и небольшие сущности с одной понятной ответственностью.
- При появлении важных долговременных архитектурных решений обновляй этот файл для будущих сессий.

## Контекст и сборка

- Проект — простой браузерный бот для пошаговой помощи со сбором ресурсов и крафтом в игре; развивай его постепенно, без преждевременного усложнения.
- Стек: TypeScript 5.x, RxJS, SWC и Rollup.
- Слои чистой архитектуры: `domain`, `application`, `infrastructure`, `presentation`.
- Сборка должна создавать один browser-loadable файл `dist/index.js`.
- Деплойный bundle должен быть максимально минифицированным; читаемый bundle не публиковать на GitHub Pages.
- `dist/index.js` деплоится на GitHub Pages через GitHub Actions.

## Архитектура и код

- Спагетти-код неприемлем: доменную логику, сценарии приложения, инфраструктуру и UI не смешивать.
- В проекте действует Observable-only подход к асинхронности: не использовать `async`/`await`, `Promise`-цепочки и Promise-ориентированные прикладные порты. HTTP-запросы, события, таймеры, отмену и композицию операций реализовывать через `Observable` и операторы RxJS; Promise-API браузера сразу оборачивать через RxJS на инфраструктурной или presentation-границе.
- Для каждой операции с `Observable` обязателен контроль жизненного цикла и аудит утечек памяти. Одноразовые потоки явно ограничивать (`take(1)`), длительные подписки хранить у владеющего контроллера и гарантированно завершать через `unsubscribe`/`takeUntil`/сигнал уничтожения; не оставлять подписки, таймеры и обработчики без teardown.
- Добыча и крафт — независимые сценарии, способные работать параллельно. Они сообщают UI о ходе работы через события use case и не управляют DOM напрямую.
- Рецепты профессий держать отдельной доменной моделью, связанной с каноническим `BotResource` через `resourceId`; цвет и уровень рецепта в UI/логах брать из связанного ресурса.
- Экземпляры из `<farm><item>` не являются отдельными ресурсами: это найденные узлы канонического `BotResource`, связанные через серверный `artikul_id`.
- При переносе curl-запроса в код сохранять только URL и HTTP-метод; cookies, session-токены и скопированные браузерные заголовки в репозиторий не добавлять.

## Канонические данные

- Рабочие локации: `Селение Баурвилл` (`area_id=6`), `Деревня Кингала` (`area_id=18`) и `Королевские усыпальницы` (`area_id=157`).
- Текущая локальная база ресурсов с постоянными id: агат, аквамарин и бирюза.
- В каноническом ресурсе отдельно хранить `articleId` узла добычи и `artifactId` предмета в рюкзаке. Текущие динамические `artifactId`: агат — `7673110639`, аквамарин — `7673111144`, бирюза — `7673110790`; автоматическое определение пока не реализовано.
- Длительность добычи хранить в каноническом ресурсе; агат, аквамарин и бирюза добываются по `20` секунд.
- Текущие рецепты: `Пыль агата` (`recipe_id=51536385`, ресурс `agate`), `Пыль аквамарина` (`recipe_id=51536386`, ресурс `aquamarine`), `Пыль бирюзы` (`recipe_id=51536387`, ресурс `turquoise`).
- Ник текущего персонажа фиксирован: `Чамодан`. Заноза — травма с `artikul_id=2299`; проверять её отдельной внутренней RxJS-функцией через `injury_info.php`, не через список обычных эффектов CanvasUser и не публиковать функцию в глобальном API.

## UI и состояние

- При загрузке показывать круглую кнопку с киркой. Она перетаскивается и сохраняет позицию в локальном браузерном хранилище.
- По клику на кирку открывать рядом небольшую тёмную игровую панель. Панель закрывается крестиком, перетаскивается, изменяет размер и сохраняет размер между перезапусками.
- Добычу и крафт держать на отдельных табах. У каждого таба свои управление процессом, лог, очистка лога без записи об очистке и контейнер progress bar; события направлять только в соответствующий таб.
- На табе добычи держать кнопку запуска, мультиселект ресурсов и одиночный селект рабочей локации.
- Выбор ресурсов, рецептов и рабочей локации сохранять в локальном браузерном хранилище.
- Для длительных действий показывать внизу соответствующего таба progress bar высотой около `10px` с названием процесса, длительностью и прогрессом. Таймеры синхронизировать с событиями use case.

## Логи

- Общий формат строки: `время: сообщение`.
- Ресурсы и мобы выводить как `Название[<level>]`, без `ур.` и пробела перед уровнем.
- Цветные имена и другие выделения рисовать жирным цветным текстом без рамки и фона.
- Успешным событиям задавать общий светло-зелёный тон строки, неуспешным — светло-красный; время оставлять нейтральным, выделения — с собственным цветом.
- На успешный старт сбора писать ровно одну строку `Начата добыча <resource> (num: <serverNumber>)`, где ресурс является цветным выделением.
- Не показывать проценты спокойности/безопасности, технические логи контрольных сканов и диагностику чтения рюкзака.

## Аварии и сирена

- При неожиданном ответе на запрос старта сбора сначала проверить занозу. Если она есть, тихо завершить добычу с соответствующим логом, без сирены; если занозы нет или проверка не удалась, обработать ответ как аварию.
- Остальные неожиданные ответы сервера на HTTP/XML-запрос считать аварией: остановить соответствующий процесс, записать красное `ТРЕБУЕТСЯ УЧАСТИЕ ЧЕЛОВЕКА` и зациклить сирену до ручного выключения.
- При старте сирены автоматически раскрывать панель и поверх всего содержимого показывать крупную красную пульсирующую кнопку тревоги.
- Клик по тревожной кнопке выключает сирену и скрывает оверлей. Постоянного toggle запуска/остановки сирены в шапке и сохранения состояния сирены быть не должно.
- В шапке держать регулятор громкости сирены: клик по иконке переключает mute, вертикальный слайдер меняет громкость, в том числе во время активной тревоги. Уровень громкости и mute между перезапусками не сохранять.
- Ответ охоты с атрибутом `time_left` считать запросом мини-игры: сохранить аварийную остановку и сирену, дополнительно выполнить `GET hunt_conf.php?mode=farm&action=minigame_get` как `Blob` и автоматически скачать исходное тело ответа без декодирования или перекодирования. Расширение изображения определять по MIME-типу или сигнатуре, неизвестный формат сохранять как `.bin`.

## Добыча

- Координаты мобов и ресурсов хранить в модели/сторе последнего скана, но не показывать без отдельной задачи.
- Опасный моб имеет `agrlevel > 0` и не является дружественным; `kind="1"` означает дружественного моба. Ресурс безопасен, если в радиусе `100px` нет опасного моба.
- Перед каждой новой итерацией перечитывать текущий выбор ресурсов, а не кэшировать его на весь запуск.
- Цикл: сканировать выбранную зону, выбрать самый безопасный доступный узел выбранного ресурса, отправить старт добычи, затем каждые `4` секунды одним контрольным сканом проверять опасность и состояние текущего узла по серверному `num`.
- Кандидатом на старт может быть только узел с `farming="0"`. Любое целое `farming != 0` означает занятый узел: хранить его в скане, но исключать из кандидатов.
- После успешного старта текущий узел с `farming="1"` означает продолжающуюся добычу; `farming="0"` — провал, исчезновение узла из `<farm>` — успех.
- Следующую добычу начинать только после успеха или провала текущей, но при терминальном результате раньше `20` секунд переходить дальше сразу.
- Progress bar начинается только после подтверждённого старта и имеет номинальную длительность ресурса (`20` секунд для текущих ресурсов). HTTP-сканы не растягивают таймлайн: после заполнения bar остаётся полным до терминального результата.
- Первичный скан не запускает и не меняет progress bar. Контрольный скан временно меняет только его лейбл, не сбрасывая таймлайн.
- Если безопасного ресурса нет, ждать `20` секунд и повторять цикл. Отмена выполняется запросом `https://w1.dwar.ru/hunt_conf.php?mode=farm&action=cancel`.
- Для каждого запроса старта генерировать новый 32-символьный hex `sig`.
- После старта читать XML `<req>`; если `first_farmer != 1`, сразу отменять добычу и не считать старт успешным.
- Stop во время активного сбора сразу визуально возвращает кнопку в состояние старта, но контрольные сканы продолжаются до терминального результата: успеха, провала, отмены или прерывания. Заполненный progress bar сам по себе отложенный stop не завершает.
- Stop во время поиска или паузы срабатывает сразу. Повторный start до терминального результата отменяет отложенный stop и продолжает текущий цикл.

## Крафт

- Крафт выполняется одним общим циклом параллельно добыче.
- Количество задаётся одним общим UI-контролом `amount`, по умолчанию `10`; перечитывать его перед каждым запросом.
- В начале общей итерации одним GET получать снимок рюкзака для всех выбранных рецептов, затем запускать каждый доступный рецепт. Не запрашивать рюкзак отдельно для каждого рецепта.
- Количество предмета читать универсально по `group` и `artifactId` из HTML `user_iframe.php`: ячейка — `span.artifact-slot[artifact_id="<artifactId>"]`, количество — `.artifact-slot-qnt`, отсутствие ячейки означает нулевой остаток. Для текущих камней использовать `group=3`.
- Для каждого доступного рецепта отправлять POST на `service_craft.php`; `amount` равен минимуму из значения UI, лимита рецепта `10` и текущего остатка ресурса за вычетом обязательного резерва в `1` единицу.
- Если доступно не более одной единицы ресурса, остановить только задачу этого рецепта и не перезапускать её в текущем запуске, пока рецепт не будет снят с выбора и выбран снова.
- После успешного запроса логировать количество рецептов и расчётный остаток ресурса; при недостатке ресурса сверх обязательного резерва логировать остановку рецепта.
- Откаты рецептов одной итерации могут идти параллельно. Progress bar каждого рецепта длится `30 секунд * amount + 5 секунд`; следующую общую итерацию начинать после завершения всех откатов текущей.
- Stop во время активного крафта сразу визуально возвращает кнопку в состояние старта, но завершает цикл только после текущих progress bar; во время паузы stop срабатывает мгновенно.
- Повторный start до завершения старых cooldown ставит продолжение в очередь; новый цикл запускается только после их завершения.
